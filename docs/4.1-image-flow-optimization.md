# 4.1 生图流程对比与优化方案

## 对比结论

当前项目的完整链路是：请求校验与路由冻结 → 任务持久化 → 本地调度 → 渠道槽位 → 账号租约/额度预检 → GPT 或 Grok 上游 → 下载/解码/转码 → 本地或 R2 媒体持久化 → 任务完成与积分结算。

参考项目的主要优势是固定 Worker、集中队列和较清晰的执行边界；当前项目的优势是任务持久化、取消、重启退款、GPT/Grok 双渠道槽位、账号租约和 R2 媒体库更完整。因此 4.1 保留现有业务链路，只借鉴参考项目的资源治理方式，不整体搬入 Redis/Python 双链路。

## 高收益优化顺序

1. **有界任务队列与固定 Worker**：把高峰请求变为有上限的等待队列，避免每个请求创建长期等待协程。队列满时明确拒绝，不扣积分、不留下幽灵任务。
2. **按真实执行方式计算槽位**：GPT 多图在账号池内逐张执行，任务只占一个槽；Grok 仅在开启并行生成时按图片数占槽，并受渠道上限约束。
3. **限制媒体阶段资源**：缩略图转码默认最多 2 路，R2 上传默认最多 4 路，避免 CPU、内存、磁盘缓冲和网络上传同时打满。
4. **阶段耗时可观测**：任务记录保存 `queue_wait`、`prepare`、`slot_wait`、`account_wait`、`upstream_and_media` 的毫秒耗时，用于区分本机排队、账号不足和上游慢。
5. **账号预检复用**：成功预检结果短期复用 60 秒；实际生成失败会立即使缓存失效，下一任务重新远端检查，减少重复刷新造成的上游压力。
6. **分档容量验证**：本地调度按 3/5/8/10/16 Worker 验证；生产并发仍需结合服务器 CPU/内存、R2 上传速度和真实上游延迟压测确定。

## 4.1 默认值

- 任务 Worker：8（重启生效）
- 等待队列：256（重启生效）
- 缩略图转码：2
- R2 上传：4
- 账号成功预检缓存：60 秒

Worker 是本机任务执行上限，不等于上游真实可用并发。账号数也不等于可承载并发；最终容量取决于账号可用额度、单账号限制、上游响应时间、媒体大小和服务器资源。

## 验证边界

本地测试覆盖队列上限、Worker 上限、关闭排空、多图槽位、任务阶段耗时、账号预检复用和 3/5/8/10/16 档调度。没有连接生产账号或真实 R2 做负载测试，也没有部署服务器。
